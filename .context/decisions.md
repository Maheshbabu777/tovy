# Decisions

One line per decision someone might later ask "why did we do it this way?" about. Newest at the bottom.

Format: `YYYY-MM-DD | decision | why | specs/<slug>.md`
2026-10-01 | GO on Expo, Legend-State v3 syncedSupabase and Supabase for the sync layer. PowerSync stays the fallback | All 9 criteria hold against the real Supabase project: offline edits sync back in 0.9 to 1.3 s, different-note and same-row conflicts converge with nothing lost, soft delete reaches offline devices, the outbox survives a restart, local writes render in 12 to 15 ms, and another user cannot read or change rows | specs/sync-spike.md
2026-10-01 | Conditions on the GO: Legend-State sync is v3 beta (3.0.0-beta.48), so pin the version and re-run the e2e suite on every upgrade. Phone persistence (SQLite in Expo Go) is untested, so check it before phase 1. Offline was simulated by blocking the network, not a real signal loss | Those are the open risks. If the beta breaks or SQLite fails in Expo Go, switch to PowerSync | specs/sync-spike.md
2026-10-01 | Real schema should keep a boolean `deleted` column for soft delete, not `deleted_at` | The Legend-State Supabase plugin expects a boolean `deleted`. Revisit if the plugin changes | specs/sync-spike.md
2026-10-01 | Dev migrations are applied by CI with the Supabase CLI on merge to `main`, never by hand. Prod is not created yet | Humans and agents cannot run SQL on the project directly, and hand-applied SQL drifted from the repo once. The one-time baseline run marked `0001` as already applied | specs/foundation.md
2026-10-01 | Sync re-fetches once the realtime channel joins (`catchUpAfterRealtime` in `src/core/sync/tasks.ts`), because the Legend-State Supabase plugin does not | A change another device saves between the first load and the channel join was missed until the next full load. Found when the faster saved-session e2e setup made test 3 fail about 1 in 4. With the catch-up: 10 of 10 alone and 4 full runs of 7 passed, against 8 of 10 and 8 of 14 before. `changesSince: 'all'` did not help | specs/auth.md
2026-10-01 | Local tasks and projects are one store per signed-in user (own IndexedDB database on web), disposed at sign out with `syncState(obs$).reset()`, never by emptying the synced observable | Clearing a single shared store was timing dependent: the plugin saves in the background, so a late write recreated the old user's note in the local database and the next user saw it (about 1 run in 4, survived a reload). Per-user stores make that impossible. `reset()` clears local data without deleting anything on the server | specs/auth.md
2026-10-01 | Sign out is `signOut({ scope: 'local' })` and warns when changes are not saved to the server yet | The default scope signs out every device. The note lets the user choose to discard unsaved edits | specs/auth.md
2026-10-02 | Every save of a store goes through one queue, one at a time in change order (`createServerWrites` in `src/core/sync/tasks.ts`) | The sync plugin sends the next save without waiting for the last, and a save takes about half a second, so quick sequences reached the server out of order (update before its insert, subtask before its parent, duplicate inserts, delete and undo applied wrongly). Found from request logs of the failing e2e runs. Trade-off: saves are slower in a long burst (one at a time), and a change to a row is skipped when the identical one was saved within 2 s | specs/tasks.md
2026-10-02 | Web hosting on Vercel (not Cloudflare Pages) | The human chose it: a free `*.vercel.app` address now, and the `.me` domain is added under the Vercel project's Domains once bought. The web app is a static Expo export, so the host can be swapped. Hobby is for non-commercial use, so revisit before real users | project-plan.md
2026-10-03 | No approval inbox. AI apps write through MCP directly; delete and remove tools are marked destructive (MCP `destructiveHint`, plus elicitation where the client supports it) so the AI app asks the user before running them. Backstops: AI tag on changed items, activity feed with undo, 30 day Trash, per app read only or read and write | The human: people live in AI apps and may not open Tovy for days, so approving in Tovy defeats the point, and the AI apps already prompt before tool calls. Todoist's official MCP also writes directly | specs/foundation-reset.md
